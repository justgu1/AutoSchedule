# ADR-002 — RLS é camada adicional, nunca a única linha de defesa

## Contexto

Row-Level Security no PostgreSQL restringe linha visível/gravável por sessão. É tentador tratar
isso como a autorização em si.

## Decisão

Autorização acontece sempre no backend primeiro (papel declarado na própria rota,
`RoleMiddleware`); RLS reforça a mesma regra no banco, pra sobreviver a um bug de aplicação ou a
um acesso direto à base — nunca é a única checagem.

```text
Rate Limiting -> Authentication -> Authorization -> DB Transaction (SET LOCAL) -> RLS -> PostgreSQL
```

A role de runtime do banco é `NOSUPERUSER NOBYPASSRLS`; `AuthContextMiddleware` seta
`app.current_user_id`/`app.current_user_role` via `SET LOCAL`, só dentro da transação da própria
request. Scheduler/worker (sem request) usam `app.is_service_context`, setado uma vez por processo.

## Consequências

- Um bug que esqueça de checar role no controller ainda é barrado no banco.
- Toda tabela sensível precisa de policy própria — RLS ausente numa tabela nova é bug silencioso
  (já aconteceu com `oauth_clients` — ver histórico de commits).
- O elo `dealership -> vehicles` é resolvido por `EXISTS` dentro da própria policy, sem copiar
  `owner_user_id` pra `vehicles` — a cópia divergiria justamente quando o admin reassocia a
  concessionária a outro seller.
